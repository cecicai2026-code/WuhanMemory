## 1. 目标清单（项目要真实做到的事）

1. 用户用日常语言描述行程，系统生成**逐日行程**，显示在**可交互的高德地图**上，包括**路线**、**交通方式**和**每个景点的详细信息**。
2. 前端 Next.js，后端 FastAPI，AI 通过 `LLMGateway` 在**通义千问（Qwen）和豆包（Doubao）之间切换**，两个都要能真实调用。
3. **数据质量规则**：
   - 每个景点必须有坐标和记录在案的来源。
   - 会变化的信息（开放时间、交通时间、票价）必须记录**上次核实时间**和**过期时间**。
   - AI 生成的每份行程，在给用户看之前，必须先用这些结构化数据校验。
4. 景点数据只用我实地去过、自己核实的信息，配我自己拍的照片。
5. **双模型对比**：同一个请求分别交给两个模型，并排比较它们给出的行程质量。
6. **批量测试**：约 20 条武汉旅行请求，每条分别跑 Qwen 和豆包，统计有多少份行程通过数据校验，输出报告。
7. **手画路线对比**：我先手工排几天的路线，再由系统的路线排序算法排同样的景点，比较总交通时间，算出差了百分之几。
8. 能让朋友和老师真正打开、试用。

### 阶段 1：景点数据和数据质量规则

- 和我商定景点数据的录入格式，建议用 `data/pois/*.json` 加 `data/photos/<poi-id>/`，方便我自己填。字段至少包括：
  - id、名称、区、类别、坐标（**注明坐标系 GCJ-02**）、建议游玩时长、介绍
  - 开放时间、票价、预约提示
  - 来源（我实地核实 / 官方网站链接）、`lastCheckedAt`、`expiresAt`
  - 照片文件名、拍摄日期
- 写一个数据检查脚本，`pnpm check:data` 或 `python -m app.tools.check_data` 都可以。它检查：
  - 缺坐标、坐标不在武汉范围内
  - 缺来源
  - 会变的字段没有 `lastCheckedAt` / `expiresAt`
  - 数据已过期
  - 照片文件不存在
- 后端 schema（`app/schemas/itinerary.py` 里的 `SourceInfo` 等）补上 `expiresAt`，并按需要拆出开放时间结构。同步更新 `packages/shared` 和 `docs/architecture/data-model.md`。
- 把数据导入 PostgreSQL/PostGIS，或者先用 JSON 仓储层、保留切换接口。**做哪种先问我。**
- 先放 2 条示例景点让我照着填。**示例里的事实性内容全部用 `TODO(Cecilia)` 占位。**

完成标准：我录入的景点全部通过 `check:data`；故意填错的数据能被查出来，并配有测试。

### 阶段 2：接入真实高德地图

- 在 `packages/map-core` 下实现 AmapProvider（JS API 2.0），替换 `MockMap`，保留 mock 作为没有 key 时的退路。
- 地图上要有：景点标记、按天区分颜色的路线折线、点标记打开景点详情（我的照片、介绍、开放时间、来源、核实日期）。
- 过期或"待确认"的信息在界面上要有明显标识。

完成标准：在本地打开首页，看到真实的武汉地图和我的景点；截图存到 `docs/screenshots/`。

### 阶段 3：路线和交通方式

- 后端调用高德 Web 服务路径规划，至少支持步行、公交地铁、驾车或打车，拿到时间、距离和折线。
- 路线结果要缓存，并记录 `checkedAt` / `expiresAt`。
- 每段路线在界面上显示交通方式、时间、距离和大致费用。

完成标准：任意两点之间能看到真实路线和几种交通方式的对比。

### 阶段 4：AI 规划链路（核心）

1. 从用户的话里抽取偏好：天数、日期、节奏、兴趣、预算、同行人、交通偏好。
2. 从我的景点库里筛出候选景点。**AI 只能从候选里选，不能自己造景点。**
3. LLM 按 schema 输出结构化行程。
4. `validate_itinerary` 校验：
   - 景点必须存在于数据库
   - 到达时间必须在开放时间内
   - 相邻景点之间要留够交通时间，时间段不能重叠
   - 每天总时长要合理
   - 用到过期数据时给出警告
5. 校验失败时，把错误反馈给模型修正一次。仍然失败就明确告诉用户哪里有问题，**不能把不合格的行程当成合格的展示**。
6. 界面上显示校验结果（通过 / 警告 / 失败，以及具体原因），并显示用的是哪个模型。

- Qwen 和豆包都要实际跑通，`.env` 里切换 `LLM_PROVIDER` 就能换模型。
- 给 `validate_itinerary` 写单元测试，覆盖闭馆、时间冲突、景点不存在、数据过期这几种情况。
- 同步更新 `docs/architecture/ai-planning-pipeline.md`。

完成标准：输入"武汉两天，喜欢历史和美食，坐地铁"，地图上出现逐日行程，并显示校验结果。

### 阶段 5：双模型对比和 20 条批量测试

- 做一个对比页面或接口：同一个请求同时交给 Qwen 和豆包，左右并排显示两份行程和它们各自的校验结果。
- 写批量测试脚本 `apps/api/app/tools/eval_models.py`：

  - 每条请求分别跑两个模型，记录：是否通过校验、出错类型、耗时、使用的景点数。
  - 输出 `eval/results/<日期>.csv` 和一份 markdown 汇总，例如"Qwen 20 条里通过 X 条，豆包通过 Y 条，最常见的错误是……"。
- 结果文件提交到 git。

完成标准：报告由脚本真实生成，可以重复运行。

### 阶段 6：路线排序算法和手画路线对比

- 实现"给定一天要去的景点，排出总交通时间最短的顺序"的算法，同时考虑开放时间。景点少时可以用穷举或动态规划，多时用启发式。**选哪种先跟我讨论。**
- 我把手工排的路线写进 `eval/manual_routes.json`。
- 写对比脚本：用同一套高德路线数据，分别计算我的路线和算法路线的总交通时间，输出每天的对比和总体差距百分比。
- 结果文件提交到 git。

## 5. 在 Claude 应用（连接到我电脑的对话）里开发时的注意事项

这个项目也会在 Claude 桌面应用里开发：Claude 通过连接的文件夹操作我 Mac 上的项目。它用的 shell 是一个 Linux 虚拟机，网络也有限制，所以：

- **不要在 Linux shell 里对项目文件夹运行 `pnpm install`、`npm install`，也不要重建 `apps/api/.venv`。** 那样会用 Linux 版本覆盖掉我 Mac 上的依赖。需要安装依赖、启动开发服务器、跑 `pnpm build`，或者调用高德、千问、豆包接口时，把完整命令写给我，我在 Mac 的终端里运行，再把结果贴回来。
- 读代码、写代码、改文档、跑不依赖安装的检查（比如 Python 语法检查、JSON 校验），可以直接在 shell 里做。
- **git**：shell 默认不能删除文件，而 git 提交时要删除临时的 lock 文件。第一次要提交前，先申请这个项目文件夹的删除权限。如果我没有同意，就把 git 命令写给我，由我在终端里执行。
- 每次开始工作前，先检查一下 `.git` 里有没有残留的 `*.lock` 文件。有的话先告诉我，不要自己硬删。
- 要我在终端里运行的命令，每次都从 `cd ~/WuhanMemory-project2` 开始写，方便我直接复制。
