# Reliability, Security, and Performance

## 可靠性

- AI 规划采用异步 job，避免请求超时。
- 每个 job 保存输入快照、工具调用日志和校验结果。
- 外部 API 超时后返回降级方案，例如只生成区域路线草案。
- 分享页绑定不可变版本，避免编辑导致分享内容变化。
- 对动态信息使用 TTL，过期后重新校验。

## 正确性

- AI 输出必须通过 JSON Schema。
- 业务校验独立于模型，例如路线连续性、时间冲突、坐标缺失。
- POI、路线、价格、开放时间都记录来源。
- 对无法确认的信息在 UI 标记为“待确认”，不伪装成事实。
- 武汉以外城市先进入实验模式，避免数据覆盖不足导致误导。

## 性能

- 外部 POI、路线、天气和内容查询进入 Redis 或数据库缓存。
- 路线矩阵批量计算，减少两两重复请求。
- 地图只渲染当前天和必要 POI，历史天可降采样。
- 分享页可静态化或边缘缓存。
- 大图、多媒体和地图 SDK 懒加载。
- pgvector 检索使用 HNSW 索引，POI 空间查询使用 PostGIS GiST 索引。

## 安全

- 高德 Web 服务 key、OpenAI key、数据库连接串只放服务端。
- 前端只能使用允许暴露的地图 JS key，并配置来源限制。
- 用户输入进入 prompt 前做长度、敏感内容和注入风险处理。
- 工具调用参数必须由 schema 校验，不能直接执行模型拼出的任意查询。
- 分享页 slug 使用不可猜测随机值。
- 删除或撤回分享页后立即失效缓存。

## 隐私

- 匿名用户只保存必要 session 数据。
- 旅行偏好可能包含家庭、儿童、健康和行程时间，默认不公开。
- 分享页发布前明确提示哪些内容会公开。
- 日志中不记录完整个人敏感信息。

## 内容合规

- 不抓取未授权评价全文。
- 评价只使用授权来源、用户自有内容或摘要化公开许可内容。
- 生成的历史文化介绍需要来源或人工审核。
- 门票、预约和支付提示必须保留更新时间。

## 观测

关键指标:

- AI job 成功率、失败率、平均耗时。
- POI 查询命中率和缓存命中率。
- 路线服务超时率。
- 行程 schema 校验失败原因。
- 分享页加载耗时。
- 地图 SDK 加载失败率。

日志需要包含:

- request id。
- conversation id。
- planning job id。
- provider call id。
- 错误 code。

## 测试策略

- 单元测试: schema、评分、时间冲突、路线连续性。
- 集成测试: POI mock、路线 mock、AI structured output mock。
- E2E 测试: 输入武汉 3 日游，生成地图行程，发布分享页。
- 合约测试: 前后端共享 API schema。
- 回归样例: 保存典型用户偏好和期望校验结果。
