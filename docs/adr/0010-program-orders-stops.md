# ADR 0010: 每天站点的顺序由程序按真实交通时间重排

日期: 2026-11-18

## 状态

Accepted（Cecilia 定，四个选择都按推荐）。在 ADR 0007 的基础上，把"模型定顺序"改成"模型给一个顺序，程序在同一天内部重排"。

## 背景

- ADR 0007 之后，模型决定每天去哪几站、什么顺序、每站待多久，程序按真实交通推钟点。顺序仍是模型凭感觉排的，提示词里只说"同一天尽量排在同一片区域，少来回跨江"。
- Cecilia 在 William Cook 的旅行商问题（TSP）网站上试过：一天 8 个地点（开放路径 8!/2 = 20160 种，回到起点 7!/2 = 2520 种），线性规划找到的路线比她手排的"先去最远的"短了约 25%。人的直觉排出来的顺序不一定省路。她又从《Algorithms to Live By》里读到：先要想清楚最小化的是什么。
- 一天最多也就六七站。8 站以内穷举所有顺序（8! = 40320）就能找到真正最短的，不用近似算法。

## 考虑过的做法

- **A. 程序直接重排（选了）**：模型只要给出每天去哪几站、待多久、几点出发；程序在每一天内部把站重排成真实交通时间最短的顺序。
- B. 只给建议：保留模型的顺序，行程卡上写"按这个顺序可省 X 分钟"。改动小，但行程本身没变好。
- C. 把最优顺序写进提示词让模型采用：第二次评测已经说明模型不一定照提示做（ADR 0007 的背景），不选。

## 决策（2026-11-18 Cecilia 定）

1. 最小化的是**这一天相邻两站之间的总交通分钟数**（高德真实时间，和推钟点、校验用同一段路线，交通方式按原来的规则选）。
2. **第一站不固定**：不知道用户住哪，按开放路径算，不回到起点。出发时间沿用模型给的，表示到达新的第一站的时间。以后加了"住在哪"再把住处当起点。
3. **错误不能变多**：比模型顺序更省时间的顺序按分钟数从少到多试，第一个"这一天的校验错误不多于模型顺序"的就用。错误数 = 推钟点 + `validate_itinerary` + 侧重规则里属于这一天的错误。所以不会为了省路把博物馆排到关门以后。
4. 分钟数一样时保留模型的顺序；不到 2 站、超过 8 站、有候选以外或重复的站、模型顺序里有一段交通没查到时，不重排。
5. 只在同一天内部换顺序，不把站挪到别的天、不增删站。修正环节照旧：模型看到的是重排后的顺序和推出的钟点，改完再重排、再推钟点、再校验。
6. 版本里 `outline` 仍存模型原样给的顺序；新加 `routeOrder`（每天：模型的顺序、程序的顺序、两边的分钟数、换没换、原因），修正过的还有 `firstRouteOrder`。`draft` 和 `days` 是重排后的。行程卡上每天写明"顺序由程序重排，少了 X 分钟"。
7. 代码在 `apps/api/app/services/planning/order.py`（纯函数）；测试在 `tests/test_route_order.py` 和 `tests/test_planning_pipeline.py`。

## 效果（`corepack pnpm eval:order`，不调用模型和高德）

用开发数据库里已经存下的行程版本、模型原样给的顺序和缓存里的高德路线算：199 个能比较的天里，程序换了 124 天的顺序；这些天路上的分钟数合计 16226 → 14595，少 10.1%；换了顺序的天，每天少的比例中位数 11.7%，最多 43.8%。结果文件 `eval/results/route-order-2026-11-18.md` 和 `.csv`。

## 理由

- 和 ADR 0007 同一个思路：模型做取舍（去哪、待多久），程序做事实和算术（交通、钟点、在给定的站里怎么走最省）。
- 穷举能保证"在这些站和这个目标下是最短的"，不是近似。

## 代价

- 双模型对比从此不再量"模型会不会排顺序"，量的是选站、停留时长和出发时间。之前和之后的评测数字不能直接比。
- 每份方案要多查同一天里两两之间的交通（两个方向）。景点间的步行和公交地铁大多已预热在缓存里；打车和没预热的会多问几次高德。
- 只最小化交通分钟数。重排以后可能因为等开门让一天总时长变长（总时长超限会算错误，不会被选中）。
- 最小化交通时间不一定是游客最想要的（例如想先去人少的地方），以后可以让用户选目标。
