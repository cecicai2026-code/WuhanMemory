# ADR 0004: 规划链路由程序编排，模型只回答固定结构，不用工具调用

日期: 2026-11-15

## 状态

Accepted（板块 5，链路设计由 Cecilia 确认）。

## 背景

- 早期设计（`ai-planning-pipeline.md` 的旧版、ADR 0002）设想让模型通过工具调用自己去查景点、路线、天气，网关里预留了 `complete_with_tools`。
- 文书要求：AI 生成的每份行程，给用户看之前必须用结构化数据校验；景点不能是编的；交通时间要真实。
- 板块 6 要把同一个请求交给千问和豆包并排比较质量。

## 决策

1. 链路的每一步由程序决定：抽偏好 → 判断要不要反问 → 筛候选 → 生成 → 查交通 → 校验 → 有错误时修正一次 → 保存。代码在 `apps/api/app/services/planning/pipeline.py`。
2. 模型只被调用三种任务（`extract_preferences`、`generate_itinerary`、`repair_itinerary`），每次都通过 `LLMGateway.complete_json` 回答一个按 Pydantic schema 校验的 JSON 对象。
3. 景点只能用候选清单里的 id；交通方式和时间由程序向高德查（`transport.py`）；预约、支付、开放时间等提示由程序从景点库取。模型不写这些事实。
4. 行程合不合格由纯函数 `validate_itinerary` 判断，不由模型自评。
5. 不做 `complete_with_tools`。

## 理由

- 程序决定查什么，就不会出现模型跳过查询、或者查了却不用结果的情况；每一步都能单独测试（单元测试用假模型和假高德）。
- 两个模型走完全一样的路、拿到完全一样的上下文，对比时差别只来自模型本身。
- 千问和豆包对工具调用的支持细节不一样，不用工具调用就不用在网关里再适配一层。

## 代价

- 候选清单整份放进提示词。现在只有 10 个景点，没问题；景点到几百个时要先按区域、兴趣筛到一个上限。
- 模型不能"想起来"去查某个它关心的信息，只能用程序给的。需要新信息时，改程序给的上下文。
