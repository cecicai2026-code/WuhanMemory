# ADR 0006: 双模型对比时，两边的输入只差模型

日期: 2026-11-15

## 状态

Accepted（板块 6，Cecilia 确认了 6 个选择，都按推荐）。

## 背景

- 文书里写"同一个请求交给两个模型并排运行，比较它们回答的质量"。要比的是模型，其余一切都要一样。
- 规划链路里偏好是模型抽出来的（ADR 0004）。两个模型各抽一次，偏好就可能不同，后面的候选、节奏、规则跟着不同，比出来的差别说不清是哪一步造成的。
- 板块 5B 一次排三种侧重的三份方案（ADR 0005）。对比时三种都排，调用次数是三倍。
- 景点资料还没实地核实，几乎每份行程都有"资料待确认"的警告。

## 决策

1. **偏好只有一份，两边共用。** 页面上用默认模型抽一次，页面写明是哪个模型抽的，这次调用不算在任何一边；批量评测的偏好手写在 `eval/requests.json` 里，由 Cecilia 确认，不调用模型。偏好里没有天数时直接让用户写清楚，不进反问的流程。
2. **一次对比只排一种侧重**，页面上可选，默认"经典必去"；批量评测每条请求写明侧重。两边走同一个 `PlanningPipeline.plan_single`：同样的候选、提示词、校验规则、修正一次。
3. **两边同时调用**，用同一个路线服务（高德请求排队、同一份缓存）。批量评测前先跑路线预热，两边查交通都走缓存。
4. **"通过"指没有错误**，警告不算。编造的景点（id 在整个景点库里都没有）和候选以外的景点（在库里但这次不能用）分开数。
5. **只列程序能算的数字**，不让一个模型给另一个打分，也不写"哪个更好"。汇总的通过率按全部运行算，模型出错的也在分母里。
6. 每次对比存进 SQLite（`model_comparisons`），两份行程各是一个不可变的行程版本。每边的模型调用用 `collect_calls`（contextvars）分开收集，不按时间去 `llm_calls` 里猜。

## 理由

- 输入完全一样，差别就只能是模型造成的，结果才讲得清楚。
- 手写的偏好让评测每次跑的输入都一样，也排除了"抽偏好的模型对自己有利"的疑问。
- 只排一种侧重，一次对比 3 到 5 次调用，批量评测 10 条请求 20 到 40 次，花得起。

## 代价

- 抽偏好这一步没有比较；页面上抽偏好的是默认模型，两边拿到的输入虽然一样，但这份偏好本身带着那个模型的理解。
- 一次只看一种侧重，侧重之间的差别要多跑几次才看得到。
- 模型每次回答有出入，每条请求只跑一次时样本很少；脚本留了 `--repeat`。
